# 公司内部 AI 平台（模拟项目）设计评审

> 由 6 个方向（安全与权限、数据与合规、模型与运维、Agent / RAG / MCP 架构、部门业务、项目范围）独立审查，汇总并审校后，按已确认的前提修订。
>
> **之后确定的决定（法域 GDPR、销售只做公司画像、HR 只抽取证据、管理层不看个人指标、写操作在模拟系统里真实执行、本地 HTML 演示界面、环境选型）都记在 [decisions.md](decisions.md)，与本文冲突时以它为准。**

## 零、已确认的前提

- **这是模拟项目**。公司、员工、客户、合同、财务、简历全部虚构，用脚本生成。不出现任何真实的个人信息或公司机密。
- **模型有两条“逻辑线路”，底层都用 DeepSeek API**：

  | 线路 | 扮演的角色 | 现在实际调用 | 以后要换真本地 |
  |---|---|---|---|
  | `local` | 公司内网部署的模型，处理 L3 / L4 | DeepSeek API | 只改配置里的 `base_url`（例如换成 Ollama / LM Studio） |
  | `external` | 外部第三方 API，处理 L1 / L2 | DeepSeek API | 不变 |

  两条线路都走 OpenAI 兼容接口，业务代码只认线路名（和 Clause Check 的 `OpenAICompatBackend` 同一个思路）。为了让模拟“看得出来”：每次调用写审计日志（级别、线路、理由）；可选让 `local` 用能力弱一些的模型来模拟能力差距；提供“本地宕机”开关和并发上限；写测试证明策略守得住。
- **数据分级用 L1–L4**（见第四节）。任何能识别具体个人的信息至少是 L3。
- **采纳的建议**：按内容而非部门分级；销售和 HR 的合规处理；权限设计（补平台管理员和服务账号、RAG 检索前过滤、Agent 调用工具时传递用户身份）；财务数字和管理层报告由代码计算；先搭底座再纵向做深 2–3 个部门。
- **不涉及**：CMO / COO（管理层按 CEO + 各部门负责人建模）；真实的硬件部署（只在设计文档里写一节“如果真实部署会怎么做”）。

## 一、总评

方向是对的。设想一开始就把“高敏走本地、低敏走 API”定为硬约束，技术栈覆盖了生产系统的主要部件，还能复用 Clause Check 的切分、Playbook、人工审批和评测。

主要问题有五个：

1. **敏感度原来是按部门划分的**。现已改为按数据内容分级（L1–L4）。销售画像和简历其实是个人数据，不能算低敏。
2. **路由和权限要在代码里强制执行**，不能靠 Agent 和提示词自觉。而且出口不只有模型调用：搜索、embedding、trace、MCP 都是出口。
3. **管理层报告会把各部门数据汇到一处**。财务和报告里的数字如果让模型去算，第一次对不上，就没人再信这个平台。
4. **“本地模型”是单点，而且通常更弱**。模拟时也要把这两点体现出来：宕机时不能悄悄改走 API，能力差距要用评测量出来。
5. **范围对一个人来说太大**。第七节给出取舍：哪些必须做出来，哪些简化，哪些只写文档。

## 二、必须先解决的关键缺口（按严重程度）

**1. 敏感度按数据内容判定，不按部门**
- **为什么**：两个方向都会出错。销售笔记里的报价、折扣底线和具名联系人，会被当成低敏发出去；法务查公开法条、技术部问通用编程问题，又会被强制走本地。
- **怎么做**：用第四节的 L1–L4 和五条规则。级别取三个来源里的最高值：数据源的默认标签；对请求内容的自动检测（正则加 NER，检测手机号、证件号、邮箱、金额、薪资、代码片段）；用户手动调高的级别。Playbook 和系统提示词本身也带标签：法务的谈判底线写进 Playbook，这份 Playbook 就是 L3，用到它的调用都必须走 `local`。

**2. 路由要有强制执行点，而且要管住所有出口**
- **为什么**：让 Agent 自己判断路由，一次误判或一次注入就会把数据发出去。例如报告 Agent 读了财务数据，再交给一个走 `external` 的子 Agent 去“润色”，数据就出去了。搜索查询词、云端 embedding、托管的 trace、第三方 MCP、IM 推送也都是出口。本地一挂，网关里某个 fallback 配置或 `try/except` 还可能“好心”把请求转给外部。
- **怎么做**：
  - 所有对外调用只走一个出口网关，Agent 不持有任何 key。仓库里维护一份出口清单，写明每个出口允许的最高级别。
  - LangGraph state 里放 `sensitivity_hwm: Annotated[int, max]`，只升不降。RAG 切块、工具返回值、子 Agent 输出、加载的 Playbook 都会抬高它。由包装代码把它写进发往网关的请求头，模型无法填写。网关只按这个值选线路。
  - 降级只有两条路：开新会话，或者经过一个显式的去敏步骤（记审计日志）。界面上提示“本会话已切换到本地模式”。
  - 失败时默认拒绝（fail-closed）：标签缺失、分类器超时，一律按高敏处理。`local` 宕机时，L3 / L4 请求排队或报错，绝不改走 `external`。
  - 发往 `external` 之前再做一道 DLP 检查（正则加 NER），只当兜底，不替代标签。
  - CI 里加金丝雀测试：在高敏测试文档里埋一个唯一字符串，跑完全量用例后扫描 `external` 出口日志，只要出现就失败。再加混沌测试：打开“本地宕机”开关发一批 L3 请求，断言 `external` 出口为 0。

**3. 法域假设要写清楚（模拟里也要写）**
- **为什么**：分级规则背后是法规。如果公司适用 GDPR，把个人数据发到境外 API 就是跨境传输。欧盟没有给中国充分性认定，需要第 46 条的保障措施。DeepSeek 隐私政策写明个人数据在中国境内处理，开放平台条款没写 API 数据的存储地。如果公司在中国境内，则要看个保法第 21、23、55 条（委托处理或单独同意，以及影响评估）。
- **怎么做**：在 README 首页写死法域假设，例如“总部在上海，有欧盟客户”。模拟里因为全是合成数据，不会真的违规，但路由规则要按这个假设实现，并在文档里说明为什么“个人信息至少 L3、只走 `local`”。

**4. 权限只在入口检查一次，Agent 会变成“混淆代理人”**
- **为什么**：如果 MCP 服务器用一个高权限服务账号，工具层就不知道是谁在请求，程序员能不能拿到 CFO 的报表只取决于提示词。低权限用户还可以借 supervisor 去调用高权限的子 Agent。
- **怎么做**：
  - 用户登录后，后端持有身份（Keycloak + 授权码 + PKCE；浏览器只拿 HttpOnly cookie）。
  - 用户身份放在 LangGraph 的运行时 context 里，由代码在调用工具时注入；工具的参数里不出现用户 id，模型无法填写。
  - 有效权限 = 用户权限 ∩ Agent 的工具白名单 ∩ 本次任务范围。MCP 服务器每次被调用都去问策略模块。
  - 每次调用 MCP 换一个短期 token（aud 是目标服务器，sub 是真人，act 是 Agent）。子 Agent 不继承父 Agent 的 token；token 原文不进 state、checkpoint 和 trace。多用户演示时 MCP 要走 HTTP 传输，不能用 stdio。

**5. RAG 先检索再过滤权限**
- **为什么**：top-k 会被无权访问的文档占满。重排、缓存、调试接口里只要漏掉一处过滤就会泄露。语义缓存还会把 A 的答案返回给 B。
- **怎么做**：
  - 每个切块带元数据：dept、level、owner_id、acl_groups、project/matter、doc_id、version、status、trust_level。
  - 过滤条件由后端按用户身份生成，下推到向量库执行，不由 LLM 生成。推荐 pgvector 加 Postgres 行级安全（RLS），应用层漏写过滤也不会泄露。注意：每个请求在事务里执行 `SET LOCAL app.principal_id = ...`；应用用非表 owner 的数据库角色连接，因为表 owner 和超级用户默认绕过 RLS。
  - 财务、法务、HR 用独立的 collection。缓存 key 带上权限指纹。权限变更（调岗、离职）按 doc_id 级联到所有副本。

**6. 销售、法务、HR、管理层的 Agent 同时具备了“致命三要素”**
- **为什么**：同一个会话既能读内部数据，又会读外部内容（网页、对方的合同、简历），还能对外通信（联网、发信，甚至前端渲染一张外链图片）。一个藏了注入指令的网页就能把数据带走，提示词挡不住。
- **怎么做**：
  - 采用 Meta 提出的 Agents Rule of Two：不可信输入、敏感数据、对外通信或改变状态，这三项在一个会话里最多占两项；三项都要时加人工审批。在 LangGraph 图上标注每个节点占了哪几项，在 CI 里自动检查。
  - 销售：联网子图只有 search / fetch 两个工具；查询由代码用公司名拼出；域名设白名单；只输出固定结构的 JSON。意向评分在另一个不联网的节点完成，不读原始网页。模拟时搜索是一个假的 MCP 服务，返回预先准备的网页，其中故意埋一段注入。
  - 法务：外部合同只进一个隔离审查节点，这个节点不能联网、不能发信。法规改为定时同步（模拟时用一份本地法规库），人工审核后入库。
  - HR：简历只进抽取节点，这个节点不能联网、不能发信。
  - 前端：设置 CSP `img-src 'self' data:`，禁止加载外部图片。外部链接显示完整 URL，点击前要确认。

**7. 管理层报告是全平台最大的数据聚合点**
- **为什么**：报告 Agent 要读所有部门的数据，汇总后比任何单一来源都敏感，还常被转发。CTO 和 CFO 有权看的范围不同。小样本统计能反推出个人，例如某部门只有 2 人时的平均薪资。
- **怎么做**：报告以请求人的身份运行，各领域的取数子图分别用请求人的权限去查，查不到的内容写明“无权限”，不悄悄跳过。不同高管的报告不共享缓存。报告继承输入中的最高级别。导出件加用户 id 和时间水印并留审计。统计设最小分组阈值（n<5 不展示）。报告 Agent 不联网，只检索审核过的文档。

**8. 数字交给模型计算**
- **为什么**：把报表、销售漏斗、项目进度向量化后让模型从文本里“读数”，会漏行、混淆期间、算错，也没法对账。
- **怎么做**：建一个指标层（指标控制在 30 个以内，每个写清定义、公式、来源、负责人、刷新频率、可见角色）。MCP 只暴露 `get_metric(name, period, dims)` 这样的参数化接口。代码先算出数字表，模型只写叙述；正文里的数字用 `{metric_id}` 占位，渲染时由代码替换，生成后检查每个数字都在数字表里。报表走“草稿 → CFO 签核 → 发布”三个状态，管理报告只引用已签核的快照。

**9. 模拟“本地模型”时要保留真实的约束**
- **为什么**：真实部署里，本地模型通常比 API 弱，而且是高敏请求的单点。如果模拟时两条线路完全一样，这两个最重要的取舍就体现不出来。
- **怎么做**：
  - 业务代码只调用逻辑别名（`local`、`external`），配置文件决定它们指向哪个模型。
  - 可选：`local` 指向能力较弱的模型，同一份评测集分别跑两条线路，把差距写进文档。
  - “本地宕机”开关和并发上限：交互请求明确提示“高敏模型维护中”，不悄悄换模型；批处理任务靠 LangGraph checkpoint 排队，恢复后从断点续跑。
  - 设计文档里写一节“如果真实部署”：模型规模与硬件的匹配、推理框架（vLLM / SGLang）、网络隔离、容量估算。不需要实现。

**10. HR 筛简历属于高风险用途**
- **为什么**：欧盟 AI 法案附件 III 第 4(a) 点把筛选求职申请、评估候选人列为高风险。GDPR 第 22 条限制有重大影响的纯自动化决策，人工确认必须有实质意义。个保法第 24 条赋予个人拒绝“仅通过自动化决策”作出重大决定的权利。中文简历里常见照片、年龄、婚育、籍贯，模型读到这些就有歧视风险。
- **怎么做**：
  - 模型只抽取字段，逐条对照岗位硬性条件，给出“满足 / 不满足 / 无法判断”，并引用简历原文。不输出总分，不自动淘汰。
  - 送进模型前去掉照片、性别、年龄、民族、婚育、籍贯、健康信息。
  - 每个淘汰决定都由 HR 在 LangGraph 的人工节点确认并写理由。
  - 反事实测试：同一份简历只改姓名、性别或年龄，结果不应变化。

**11. trace、checkpoint、缓存是没有纳入权限管理的“第二个数据库”**
- **为什么**：Langfuse 默认记录完整输入输出，checkpointer 会保存整个 state。能看 trace 的人，实际上拥有全公司最高的数据权限。另外，trace 回答不了“谁、以谁的身份、通过哪个 Agent、看了什么、谁批准的”，内容也可以被删改，不能当审计日志用。
- **怎么做**：trace 按部门分项目；L3 内容脱敏后记录，L4 只记元数据（谁、何时、做了什么）。业务主管只看本部门的聚合指标，不看逐条内容。另建一张只追加的审计表（真人、代理链、工具、资源、策略决定、审批 id、路由理由），加哈希链防篡改。checkpoint 设过期时间。

**12. 写操作没有分级审批**
- **为什么**：发邮件、合并代码、发出合同、财务过账都很难撤销。审批界面如果只显示模型写的摘要，摘要可能和真实参数不一致；审批之后参数被改，也是常见漏洞。
- **怎么做**：工具分三级：只读；内部可撤销（建草稿、开 PR）；对外或不可逆。第三级必须经过 LangGraph interrupt 人工审批。审批界面显示真实参数（完整收件人、附件、diff、金额），审批记录绑定参数哈希，执行时校验。四眼原则：请求人不能批准自己的请求。写工具只返回 proposal_id，由后端在人确认后执行。

**13. 没有评测集和上线门禁**
- **为什么**：没有评测，就回答不了“`local` 模型能不能做合同初审”“改了 Playbook 后有没有变差”，也证明不了“程序员问不到财务数据”。对作品集来说，这些测试结果是最能体现“像生产”的证据。
- **怎么做**：
  - 每个用例准备 30–100 条黄金数据，取自模拟公司数据（第七节在数据里埋下的问题就是标准答案）。指标按用例定：销售意向看准确率和混淆矩阵；财务要求数字和 SQL 结果完全一致；法务沿用 Clause Check 的评测；HR 看抽取准确率和组间差异；管理层报告看埋入问题的检出率和数字校验通过率。
  - 安全测试分四类：权限矩阵（角色 × 资源 × 操作，覆盖聊天、每个 MCP 工具、向量检索、报告导出）、路由样本、金丝雀和混沌测试、注入红队集。
  - CI 门禁：模型、提示词、Playbook 的任何变更，各用例不能低于基线减阈值；安全测试必须全部通过。

## 三、其余缺口（按领域）

**安全与权限**
- 凭据只在工具执行层注入，模型永远看不到；工具返回值过滤形似 token 的字符串。按用途分 key、设消费上限；pre-commit 加 gitleaks。
- 账号生命周期：员工调岗、离职时吊销 token、清空缓存和会话，并测试吊销后所有接口都拒绝访问。
- RAG 投毒：员工上传的文档、工单、代码里的 README 也会被检索给别人。每份文档标信任等级；管理报告和 Playbook 只检索审核过的集合。长期记忆按用户隔离。
- 代码在一次性容器里执行：不联网、不挂载凭据、限时。
- 限时委托和紧急访问（break-glass）要填理由、自动过期，并在审计日志里高亮。
- 演示用的“切换身份”本身就是提权入口，只在 demo 配置里开启，并写审计。

**数据与合规**
- 每个切块和每条 trace 都带 subject_id。删除某人数据时覆盖向量库、checkpoint、trace 和缓存。
- 销售画像属于 GDPR 意义上的画像：需要正当利益评估、告知义务（第 14 条）和反对权（第 21 条）。数据来源设白名单，禁止抓取 LinkedIn（用户协议禁止）。每条事实保存来源 URL。模拟时只对虚构的人和公司操作。
- 法规库标状态：已生效 / 已通过未适用 / 草案。回答引用条款号，检索失败就明确说“未能获取”。
- 如果按人统计进度并用于考核或派活，可能落入 AI 法案附件 III 第 4(b) 点（监控和评估员工表现）。报告默认按项目粒度汇总，trace 不得用于绩效考核。
- 仓库里放一个 `compliance/` 目录：处理活动记录、影响评估、出口清单、保留期矩阵、路由测试报告。

**模型与运维**
- 网关按部门设预算和限流；设重试（指数退避）、超时和熔断。
- 维护模型清单：API 的模型名可能在你不改代码时换掉背后的模型（DeepSeek 的 changelog 有过先例），每天跑一次回归评测。
- 保持 Playbook 和系统提示词这部分前缀稳定，提高 DeepSeek 上下文缓存的命中率。
- `external` 不可用时，L1 / L2 请求可以改走 `local`，这个方向是安全的，但要记录。反方向绝不允许。

**Playbook**（你列了这个组件，设想里还没展开）
- 把 Clause Check 的“规则即数据”推广到每个部门，每个 Playbook 都是带 schema 的数据文件：
  - 销售：低、中、高意向各自的跟进策略、触达频率、可以承诺的内容。
  - 技术：需求、立项、前后端、测试、上线、运维每个阶段的准入和完成标准，AI 按它检查工单是否齐全。
  - 法务：审查立场和可接受的 fallback 条款（复用 Clause Check），以及初拟合同用的条款库和模板。
  - 财务：月结检查清单和对账规则。
  - HR：岗位硬性条件清单，只放可以核验的条件。
- 治理：每个 Playbook 有负责人（部门负责人）、版本、状态（草稿 / 生效 / 停用）、评测集和敏感度级别。基层可以提修改建议，负责人批准；生效前先跑评测。每个输出记录 `playbook_id@version`。

**多 Agent、LangGraph 与 MCP**
- 不要用一个挂满所有工具的 supervisor。第一层由代码按身份和意图路由；各部门的固定流程（合同审查、月结、招聘初筛、需求到上线）用确定性的 LangGraph 子图；自主 Agent 只用于调研、代码问答和文档问答。
- 真正需要多 Agent 的地方有两处：管理层报告（各领域取数子图并行，各自用请求人权限，最后交给一个不带工具的写作节点）；销售调研（隔离的联网子 Agent + 不联网的评分节点）。
- 跨部门协作用工单式交接，只传最少必要的字段，例如“线索 → 法务审合同 → 财务开票 → 技术立项”“用人需求 → 部门负责人核预算 → CEO 审批 → 招聘”。这正好补上设想里缺的跨部门主线，也是演示多 Agent 和权限边界的好素材。
- LangGraph 用到的部件：运行时 context 放用户身份；state 里放 `sensitivity_hwm`；`interrupt` 做审批；PostgresSaver 做 checkpoint（设过期时间），支撑断点续跑；Store 只存个人偏好。
- MCP 按数据域划分（crm / code / docs / finance / hris / legal / web），读写分离。真正的拦截在每次调用时做。

**各部门业务**
- **销售**：公开信息只能说明客户合不合适（匹配度），购买意向要看 CRM 里的互动记录。拆成两个分数，由代码按规则计算。同名客户用“公司 + 职务”消歧，并用模拟数据回测。
- **技术**：进度只取自工单、Git 和 CI（先用模拟工单表）。AI 负责汇总和发现不一致，例如工单显示“测试完成”，CI 却一直是红的。代码助手不必自己造：支持自定义 OpenAI 兼容端点的 IDE 插件可以接到网关的 `local` 线路，平台只提供代码库 RAG 和工单 MCP。
- **法务**：整理历史文件沿用学过的解析升级路线（规则 → 版面模型 → 大模型 → 人工）。把对方名称、签署日、到期日、管辖法律、自动续约等字段抽进结构化表，“下月到期的合同”才能用 SQL 查出来。初拟合同从审核过的条款库和模板拼装，模型只填变量、按 Playbook 选 fallback 条款，不让模型从零自由起草。
- **财务**：所有统计由 SQL / 代码完成，做确定性对账，保留审计痕迹。
- **HR**：编制需求按字段拆开：只含岗位和人数的部分是 L2，带薪酬预算的部分是 L3。

**组织设定**
- 补齐角色：平台管理员（管系统，默认看不到业务内容）、安全审计员（只读审计日志）、每个后台任务一个服务账号。

## 四、数据分级与路由

### 1. 四个级别

| 级别 | 含义 | 典型内容 | 线路 | 日志与 trace |
|---|---|---|---|---|
| L1 公开 | 已经公开或可以公开 | 公司官网和新闻、公开法规、已发布的招聘 JD | `external` 可用 | 正常记录 |
| L2 内部 | 内部使用，泄露危害小，不含个人信息 | 内部制度、通用模板、不带公司代码的技术问答 | `external` 可用（发出前自动检测） | 正常记录 |
| L3 机密 | 泄露会造成损害，含具体个人的信息或商业机密 | 客户联系人画像、源代码、合同、报价折扣、项目计划、候选人简历、日常账务 | 只能 `local` | 脱敏后记录 |
| L4 绝密 | 泄露危害严重，极少数人能看 | 薪资、绩效、简历评估结论、财务报表与融资、诉讼纠纷、安全漏洞 | 只能 `local` | 只记元数据 |

### 2. 五条规则

1. **个人信息规则**：能识别出具体某个人的信息，至少是 L3。
2. **就高不就低**：请求、文档、报告的级别，取用到的所有数据里最高的一级。
3. **只能升级，不能降级**：员工可以调高；调低只能由数据负责人或管理员操作，并留审计。
4. **按来源给默认值，按内容自动升级**：每个系统或文件夹有默认级别；检测器发现个人信息、金额、薪资、代码时自动升级；拿不准按更高的级别处理。
5. **密钥永远不进模型**：发给任何模型之前都删掉。

`local` 宕机时，L3 / L4 请求排队或报错，绝不改走 `external`。

### 3. 路由示例

| 部门 | 请求示例 | 级别 | 线路 |
|---|---|---|---|
| 销售 | 只用公司名查官网、融资、新闻 | L1 | external |
| 销售 | 给某位具体联系人建画像、判断意向 | L3 | local |
| 销售 | 结合历史报价和折扣给跟进策略 | L3 | local |
| 技术 | 通用编程问题，不贴公司代码 | L2 | external |
| 技术 | 解释或重构公司代码；带用户手机号的日志 | L3 | local |
| 技术 | 分析安全漏洞 | L4 | local |
| 法务 | 查 GDPR 条文和监管指南 | L1 | external（或法规库） |
| 法务 | 问“符合 GDPR 吗”，同时粘贴客户合同条款 | L3 | local（问题公开，内容机密，取最高） |
| 法务 | 按 Playbook 初审合同 | L3 | local（Playbook 本身就是 L3） |
| 法务 | 整理诉讼材料 | L4 | local |
| 财务 | “什么是递延收入” | L1 | external |
| 财务 | 汇总本月费用明细 | L3 | local，数字由 SQL 计算 |
| 财务 | 生成季度财务报表 | L4 | local，数字由 SQL 计算 |
| HR | 起草公开 JD（不含薪资预算） | L2 | external |
| HR | 汇总编制需求 | L2 / L3 | 只含岗位人数走 external；带薪酬预算走 local |
| HR | 初筛简历 | L3（筛选结论 L4） | local |
| HR | 整理薪资和绩效 | L4 | local |
| 管理层 | 行业趋势研究（不带内部数据） | L1 | external |
| 管理层 | 各部门人数、项目进度汇总（去掉个人信息） | L3 | local |
| 管理层 | 含财务和薪资的经营报告 | L4 | local |
| 任意 | 前两轮是公开问题，第 3 步拉入 CRM 数据 | L1→L3 | 从第 3 步起全部 local，开新会话才重置 |
| 任意 | 标签缺失、分类器超时、local 宕机 | 未知 | local 或排队，绝不走 external |

## 五、权限模型

**角色**：`employee@部门`、`manager@部门`（CTO、CFO 等即对应部门负责人）、`ceo`、`platform_admin`、`security_auditor`、服务账号（每个后台任务一个）。另有三种关系属性：项目成员、案件承办人、汇报线。

**数据标签**（每个切块、每行数据、每个工具返回值都带）：`level`、`dept`、`owner_id`、`acl_groups`、`project_id/matter_id`、`trust_level`。

| 数据 | 级别 | 本部门基层 | 本部门负责人 | 其他部门 | CEO | 平台管理员 |
|---|---|---|---|---|---|---|
| 公开资料、法规库 | L1 | 读 | 读 | 读 | 读 | 运维，不读内容 |
| CRM 客户、商机 | L3 | 自己负责的客户 | 全部门 | 法务凭工单临时查看单个客户 | 汇总，可钻取 | 否 |
| 源码、工单 | L3 | 所在项目 | 全部门 | 销售可看项目阶段级进度 | 项目级汇总 | 否 |
| 合同库 | L3 | 自己承办的 | 全部 | 销售可看自己提交的合同状态 | 读 | 否 |
| 诉讼与律师工作文件 | L4 | 承办人 | 读 | 否 | 需单独授权 | 否 |
| 总账、报表 | L3–L4 | 读，写草稿 | 签核 | 只看已发布的指标 | 读 | 否 |
| 薪酬、员工档案 | L4 | 经办字段，薪资屏蔽 | 读 | 经理可看直属下级的非薪资字段 | 部门级汇总（n<5 不展示） | 否 |
| 简历、候选人 | L3–L4 | 经办岗位 | 读 | 用人经理看本岗位候选人 | 默认否 | 否 |
| 管理层报告 | 继承最高 | 否 | 本领域报告 | 各负责人按自己的权限取数 | 全部 | 否 |
| Playbook | 按内容 | 读，可提建议 | 批准发布 | 按级别 | 读 | 否 |
| trace 内容 | 继承 | 否 | 只看本部门聚合指标 | 否 | 否 | 只看脱敏元数据；排障看原文走 break-glass |
| 审计日志 | — | 否 | 否 | 否 | 否 | 否（只有安全审计员可读） |

**RAG 检索怎么过滤**：
1. 网关从 token 里解析出用户身份，策略模块据此生成可访问的 collection 列表和过滤条件（级别上限、部门、acl_groups、项目/案件）。过滤条件不由 LLM 生成。
2. 只查询有权访问的 collection，过滤条件下推到向量库执行，再用 Postgres RLS 兜底。
3. 只检索现行版本；管理报告和 Playbook 只检索 `trust_level=reviewed` 的文档。
4. 召回结果中的最高级别并入 `sensitivity_hwm`，决定后续调用走哪条线路。
5. 测试：用 6 个部门 × 2 个层级的账号问同一个问题，断言各自返回的 doc_id 集合符合预期。

## 七、作品集落地路线

**先做取舍**：一个人做不完上面全部，分三档。

| 档位 | 内容 |
|---|---|
| 必须做出来 | 出口网关 + 只升不降的路由 + fail-closed；pgvector + RLS 检索前过滤；用户身份注入 + 每次工具调用查策略；LangGraph interrupt 审批；只追加的审计表；指标层（数字由 SQL 计算）；评测和安全测试进 CI |
| 简化做 | 策略引擎先用一个 Python 模块（单一入口函数 + 表驱动测试），接口留给 OPA / Cedar 替换；短期调用 token 先由后端自己签发（aud、sub、act 齐全），以后再换成 Keycloak 的 token 交换；DLP 用正则加一个 NER；指标层先用 SQL 视图加一份指标定义 YAML；工单先用模拟表；密钥用 Docker secrets 加 gitleaks；监控先用 trace 平台自带的指标 |
| 只写文档 | 真实部署时的模型与硬件选型、容量和成本、SLO 和 runbook、break-glass 流程、mTLS、合规文档（影响评估、处理活动记录、保留期矩阵） |

**M1 平台骨架 + 模拟公司**（最能体现“像生产”，工作量最大）
- 内容：身份认证（用脚本生成约 70 个账号，测试只需 6 部门 × 2 层级共 12 个）；策略模块；出口网关和两条线路；只升不降的路由和 fail-closed；pgvector + RLS；trace；审计表；一个最简单的问答场景，要同时用到两条线路。
- 演示：公开问题走 `external`，带内部数据的问题走 `local`，审计日志可查；切换身份问同一个问题，返回的文档不同；打开“本地宕机”开关发一批 L3 请求，`external` 出口为 0；权限矩阵、路由和金丝雀测试在 CI 里全部通过。

**M2 法务合同审查**（复用 Clause Check）
- 内容：合同库 RAG（带版本状态和结构化的到期字段）、本地法规库、隔离审查节点、律师审批（四眼）、引用可跳转到原文、用条款库初拟合同。
- 演示：一份藏了注入指令的合同被隔离，没有产生任何越权工具调用；“下月到期的合同”能用 SQL 准确查出。

**M3 管理层报告 + 财务指标层**
- 内容：指标层、模拟总账和对账、按请求人身份取数、数字校验、导出水印。
- 演示：CEO 和 CTO 拿到不同的报告；每个数字都能点回来源；剧本里预先埋下的问题被报告发现。

**M4 销售画像 + HR 轻量版**
- 销售：联网子图走 `external`，联系人画像在 `local`；匹配度和意向两个分数，并做回测；按意向分级套用 Playbook。
- HR：编制需求汇总；简历结构化，加人工确认和偏差测试报告。
- 补齐 `compliance/` 目录。

**最小可交付**：时间不够时，M1 + M2 已经是完整的作品集。M3、M4 是加分项。

**模拟数据怎么造**
- 先写一份“公司剧本”：公司名和产品、约 70 人的名册、12 个月的业务时间线、法域假设。
- 用脚本生成各系统的数据，客户 ID、项目 ID、员工 ID 在各系统间共用。
- 故意埋入已知问题作为评测答案：大客户回款逾期、合同下月到期、某项目测试阶段延期、某部门招聘超预算、某份合同缺数据处理条款，再加几份带注入的网页、合同和简历。
- CRM 和 HRIS 用 Postgres 表，外面各包一个 MCP 服务。所有个人信息都是虚构的。

## 九、事实核查（审查时查证过的要点）

- **DeepSeek**：隐私政策写明个人数据在中国境内处理；开放平台条款没写 API 数据的存储地和保留期；API 没有官方 embedding 接口；官方 changelog 显示 API 模型名背后的模型会更新。
- **安全研究**：“致命三要素”（Simon Willison，2025-06）；Agents Rule of Two（Meta，2025-10）；OWASP LLM08:2025（向量与 embedding 弱点）。
- **法规**：GDPR 第 14、21、22 条及序言第 71 段，欧盟没有给中国充分性认定；欧盟 AI 法案附件 III 第 4 点；个保法第 21、23、24、55 条；LinkedIn 用户协议禁止抓取。
- **不确定，需要后续核实**：DeepSeek API 数据的实际存储地、是否用于训练、保留期；欧盟数字综合法案对 AI 法案义务的推迟（来自律所解读，没有核对官方公报）；MCP 授权规范的最新修订版本。
