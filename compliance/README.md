# GDPR documentation for the ABC Tech AI platform

This folder holds the data protection paperwork a real controller would keep for the internal AI platform in this repository. ABC Tech AB is fictional (Stockholm, Sweden, about 70 staff; [docs/company.md](../docs/company.md)), and every person, résumé, contract and figure in the platform is generated by `corpai/synth` (decision D1). The documents still follow the real rules (GDPR, the Swedish Data Protection Act 2018:218, the EU AI Act, Swedish labour law) and describe the real code, so they show what the platform does today and what a real deployment would still need.

Everything here was derived from the code, the configuration and the docs as of 2026-10-08 (commit `94a4458` plus the wrap-up working tree). When this folder and the code disagree, the code is right and this folder needs an update.

## Roles

**Controller.** ABC Tech AB, Stockholm, Sweden, for everything the platform processes: staff using it, people named in internal documents, business contacts in the CRM, job candidates. Contact: the privacy team, `privacy@abctech.example` (the company's data protection policy, `gen-data-protection-policy` in the synthetic corpus, sends data subject requests there).

**Supervisory authority.** IMY (Integritetsskyddsmyndigheten), Sweden. The company also has an engineering hub in Warsaw. If that hub is an establishment of ABC Tech AB, processing that involves Warsaw staff is cross-border and IMY acts as lead supervisory authority (Art. 56), with the Polish authority (UODO) concerned. **[counsel]**

**Data protection officer.** None appointed. Whether Art. 37 requires one turns on FleetPilot, the product: ABC Tech processes its customers' driver location data as their processor, and that is outside this platform. **[counsel]**

### Both model routes reach DeepSeek today (decision D3)

The design sends personal data (L3) and restricted data (L4) only to the `local` route, which stands for a model that runs inside ABC Tech's own network. In this simulation `local` is the same DeepSeek API as `external` ([config/models.yaml](../config/models.yaml) `simulated_onprem: true`; [config/egress.yaml](../config/egress.yaml) `model.local`, host `api.deepseek.com`, `max_level: L4`). The routing, audit and fail-closed rules run exactly as they would on-prem, but the data leaves the machine either way.

With synthetic data this is harmless. With real data it would mean:

- **Both routes are a third-country transfer.** DeepSeek processes data in China (its privacy policy says so for personal data; its API terms do not name a storage location, design-review §9). The EU has no adequacy decision for China, so every transfer needs an Art. 46 safeguard (standard contractual clauses) and a transfer impact assessment. Whether such an assessment can come out positive for this recipient is doubtful. **[counsel]**
- **Both routes are a processor relationship.** That needs an Art. 28 contract with DeepSeek. None exists: the simulation runs on a developer API key with synthetic data.
- **The `local` route would carry the most sensitive data out of the EU.** That includes redacted résumés and the HR screening prompts, contract text and CRM contacts. Special-category data can slip through the résumé redaction (see the DPIA, R1 and R11).
- **Local calls are not in the egress log.** `ops.egress_log` records only `external` calls, because `local` is meant to stay inside the company. Local calls appear only as `model_call` audit rows (metadata, no text).

**Rule for a real deployment [recommendation]:** no personal data of real people enters the platform until `local` points at a model ABC Tech runs itself (on-prem or in an EU environment it controls), or at a provider with an Art. 28 contract and a working Chapter V transfer mechanism. Moving `local` changes only its `base_url`/`model` in `config/models.yaml` and its host in `config/egress.yaml`; no business code changes.

## What is not done yet

These gaps recur across the documents. None of them matters for synthetic data. Each one has to be closed before real people's data is used.

1. **The `local` route is a third-party API in another country** (see above).
2. **Retention is implemented for two stores only.** Checkpoints are pruned by a command that nothing schedules; legal uploads expire from memory after 2 hours. Every other store keeps data indefinitely ([retention-matrix.md](retention-matrix.md)).
3. **Erasure reaches traces only partly.** Tool and retrieval spans now record the `subject_ids` of what they read, and the owner function `trace.erase_subject()` blanks every run of the threads that touched the person (migration 103, issues-log D-04). Model calls made by domain code record no subject, though. The HR screening prompts (the redacted résumé, kept as L3-masked text in the HR user's `llm` spans) are the main case, and `trace.erase_subject('CAND-…')` does not find them. `legal.reviews` and checkpoints are not indexed by data subject either.
4. **There is no tooling for access or erasure requests.** The `subject_ids` label column exists on most content tables, but apart from `trace.erase_subject` no job compiles or deletes by it.
5. **Candidates and business contacts are not informed.** There is no candidate notice about AI-assisted screening (Art. 13, AI Act Art. 26(11)), and follow-up e-mails carry no Art. 14 notice and no opt-out line.
6. **There is no suppression list for direct marketing.** `crm.contacts` has no do-not-contact flag, and the `crm.send_email` executor checks none (Art. 21(2)–(3)).
7. **The hiring manager's candidate view shows the unredacted résumé.** Since issues-log WR-17 it carries a bias notice, but the text is not redacted.

Closed in the final review (issues-log section 十五): Swedish résumé labels, sexual orientation and transgender identity are now redacted (DPIA R11); the `hr_screening` audit row records only how many protected-attribute kinds were removed, not which (R10); LangSmith tracing is forced off whenever `corpai` is imported ([egress-inventory.md](egress-inventory.md)).

## Open questions for counsel

- A transfer mechanism and transfer impact assessment for DeepSeek, or a decision not to use it for personal data at all.
- Whether ABC Tech, which builds the screening system for its own use, is also its **provider** under the AI Act (Art. 3(3)), with the provider obligations that follow (DPIA §8).
- When the AI Act's Annex III obligations apply. The Regulation as published says 2 August 2026, and a 2025 Commission proposal would postpone them. Check the Official Journal.
- Whether the MBL negotiation duty (§11 or §13) applies, which depends on whether ABC Tech is bound by a collective agreement.
- B2B e-mail rules for recipients in Germany and the other customer countries ([lia-sales-profiling.md](lia-sales-profiling.md) §7).
- Retention periods for recruitment records and for the audit log.

## 中文摘要（给项目负责人）

> 虚构公司、合成数据，仅作示例，不构成法律意见。

这个目录是模拟公司 ABC Tech AB（斯德哥尔摩，监管机构是瑞典的 IMY）的 GDPR 合规文档，内容全部从代码、配置和已有文档推出来。凡是标 **[recommendation]** 的地方，代码里都还没有做。

- **ropa.md**：处理活动记录（第 30 条），共 11 项，包括知识问答、合同审查、管理层报告、销售画像、HR 编制说明、简历筛查、用人经理看候选人、审计、trace、演示录制和账号会话。
- **dpia-hr-screening.md**：简历筛查的影响评估（第 35 条）。按 `hr_screening` 的实际流程写，还写了瑞典《反歧视法》、第 22 条（`hr_decision` 由人做决定）、MBL §11 与员工代表协商，以及欧盟 AI 法案把招聘列为高风险用途后，部署方要承担的义务。
- **lia-sales-profiling.md**：销售画像的正当利益评估（第 6(1)(f) 条）、第 14 条的告知义务，以及瑞典和德国对 B2B 营销邮件的规定（需要律师核实）。
- **egress-inventory.md**：数据出口清单。列出每个出口允许的最高级别、发出去的是什么数据、是否跨境，以及由哪段代码拦截。
- **retention-matrix.md**：每个数据存储的保留期限、实际已实现的删除机制，以及访问、删除、反对这几项权利怎样处理。

最重要的一点（决定 D3）：现在 `local` 和 `external` 两条线路都调用 DeepSeek。用合成数据没有问题；如果换成真实数据，两条线路都是向中国的跨境传输，也都构成受托处理关系，需要第 28 条的合同、第 46 条的保障措施和传输影响评估。所以真实部署之前，`local` 必须先换成公司自己控制的本地或欧盟内的模型。

核对时发现、还没修的问题：
1. **HR 筛查的提示词进了 trace，但删除请求找不到**：脱敏后的简历按 L3 遮蔽后，留在 HR 用户的 `llm` span 里，这些 span 没有记录候选人编号，所以 `trace.erase_subject` 删不到。工具调用和检索的 span 已经记录 `subject_ids`（迁移 103，D-04），可以删除。
2. **保留期基本没实现**：除了 checkpoint（要手动运行 `prune`）和法务上传（内存里保留 2 小时），其他存储都永久保留。
3. **候选人告知、营销邮件的退订和告知文字、数据主体请求的工具都还没有。**

终审已修（问题记录第十五节）：瑞典语简历字段、性取向和跨性别身份现在会脱敏（R11）；`hr_screening` 审计记录只写去掉了几类受保护属性，不写是哪几类（R10）；只要导入 `corpai`，LangSmith 追踪就被强制关闭。
