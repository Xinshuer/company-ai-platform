## Facts that apply to every activity

These hold for all eleven activities, so the entries below do not repeat them.

- **Transfers.** Any model call goes through `ModelGateway.chat` ([corpai/gateway/gateway.py](../corpai/gateway/gateway.py)). The gateway picks the route from the data level: `external` for L1/L2, `local` for L3/L4. **Today both routes call the DeepSeek API in China** (decision D3), so any activity that calls a model is a third-country transfer to a processor. That is harmless with synthetic data and not acceptable with real data ([README.md](README.md), [egress-inventory.md](egress-inventory.md)). The gateway sends the provider no user identifier: `BackendCall` carries no principal ([corpai/gateway/backend.py](../corpai/gateway/backend.py)).
- **Who can see what.** Every content row carries a label (level, ACL groups, trust, `subject_ids`), and PostgreSQL row-level security filters every query by the caller's clearance and groups (architecture §4–§5.1). "Recipients" below therefore lists roles, not individuals.
- **Logs created by every activity.** Each model call, tool call, retrieval and policy decision writes an audit row (activity 8), and each graph node writes trace spans (activity 9). Each run keeps its state in LangGraph checkpoints owned by the user (retention: [retention-matrix.md](retention-matrix.md)).
- **Synthetic data.** All data subjects below are generated by `corpai/synth` (decision D1). The categories describe what the same processing would hold in a real deployment.
- **Employees as data subjects.** Swedish employers can rarely rely on employee consent (there is an imbalance of power), so no activity uses consent as its legal basis.

## 1. Q&A over internal documents (`qa`)

**What it does.** A member of staff asks a question. The graph classifies it, retrieves passages the user may read, may call up to three rounds of read-only tools, and answers with citations ([corpai/agents/qa.py](../corpai/agents/qa.py); architecture §16 M1).

| | |
|---|---|
| Purpose | Let staff find internal policies, documentation and business facts they are already allowed to see. |
| Legal basis | Art. 6(1)(f): ABC Tech's interest in efficient access to its own information. The user only reaches data their role already grants, so the expectations of the people named in it barely change. Art. 9: not intended. HR staff may retrieve HR documents that mention health or family matters, which is covered for HR's employment-law work by Art. 9(2)(b) with the Swedish Data Protection Act (2018:218) ch. 3 s. 2. **[counsel]** |
| Data subjects | Staff (the asking user; people named in documents and tickets); business contacts at customers, when a sales user's tools return CRM rows they own. |
| Personal data | The user's id, department and question; names, roles and contact details inside retrieved passages and tool results (CRM accounts with contacts; headcount aggregates only). |
| Sources | `rag.documents`/`rag.chunks` in the collections the `qa` purpose allows (`public`, `general`, `legal_regs` and the user's own department), and MCP read tools listed for `qa` in [config/agents.yaml](../config/agents.yaml). |
| Recipients | The user only. The answer is not shared. The model provider receives the prompt (route by level). |
| Transfers | `external` when the whole prompt is L1/L2; `local` as soon as anything is L3 or higher (any recognised person name is L3, decision D4). |
| Retention | Checkpoints (question, passages, answer): 30 days idle, then `python -m corpai prune`. Audit and trace: no limit yet. `ops.egress_log` keeps the full payload of external calls. See [retention-matrix.md](retention-matrix.md). |
| TOMs | **[implemented]** RLS on every collection ([corpai/rag/retrieve.py](../corpai/rag/retrieve.py); the `rag_filter` purpose in [corpai/policy/engine.py](../corpai/policy/engine.py)); person-name gazetteer so names classify as L3 ([corpai/classify/](../corpai/classify/)); secrets scrubbed before any model call; L4 citations without snippets; passages addressing AI systems withheld ([corpai/agents/_qa_guard.py](../corpai/agents/_qa_guard.py)); embeddings computed locally (`corpai/embed`), so queries never leave the process for retrieval. Tests: `tests/security/test_permission_matrix*.py`, `tests/security/test_canary.py`, `evals/qa`. |
| Gaps | Unrecognised names (people not in `core.users`, `crm.contacts` or `hr.candidates`) can stay L2 and go `external` **[partial]**. |

## 2. Legal contract review (`legal_review`)

**What it does.** There are four modes ([corpai/agents/legal/graph.py](../corpai/agents/legal/graph.py); architecture §16 M2). *Review* checks a stored, pasted or uploaded contract clause by clause against the legal playbook (Clause Check) and stores the result. *Due* lists contracts whose notice deadline falls in a month, in SQL only. *Draft* assembles a contract from templates, with one optional model call, and files it as a tier-2 proposal. *Send* files a tier-3 (four-eyes) proposal that writes the contract to the simulated outbox.

| | |
|---|---|
| Purpose | Contract management: spotting unacceptable positions and missing data processing terms, keeping notice deadlines, preparing and sending contracts. |
| Legal basis | Art. 6(1)(f) for reviewing and managing contracts and for establishing or defending legal claims; Art. 6(1)(b) where the counterparty is a natural person (sole trader) and the processing is needed for the contract. Litigation matters (`legal.matters`, L4) are not part of the review flow. |
| Data subjects | Counterparty staff and signatories named in contracts; ABC Tech lawyers and requesters; contacts receiving a sent contract. |
| Personal data | Names, titles and business contact details in contract text; the reviewer's and requester's ids; the recipient address of a sent contract. |
| Sources | `legal.contracts` (as the user, RLS), pasted text, uploads (`POST /api/legal/uploads`), `legal.clause_library`, the playbook ([corpai/legal/data/](../corpai/legal/data/)). |
| Recipients | The requester, the handling lawyer and the head of legal (`legal.reviews` ACL, `migrations/080_m2_legal_reviews.sql`); approvers of draft and send proposals; the counterparty contact (simulated outbox). |
| Transfers | Review and draft run at L3 or higher, so `local` only. Due and send make no model call. |
| Retention | Uploads: process memory, 2 hours, at most 10 per user ([corpai/agents/legal/uploads.py](../corpai/agents/legal/uploads.py)) **[implemented]**. `legal.reviews`: immutable, no deletion **[recommendation: a retention period tied to the contract's life]**. Proposals and outbox rows: no deletion. |
| TOMs | **[implemented]** The review node holds no MCP tool and nothing outbound (Rule of Two); its model loop has only Clause Check's in-process lookups ([corpai/legal/clausecheck/tools.py](../corpai/legal/clausecheck/tools.py)). Embedded instructions in contracts are flagged with no effect ([corpai/legal/injection.py](../corpai/legal/injection.py)). Reviews are stored only through `legal.save_review()` (actor from the session). Sending is four-eyes. The legal pages' direct reads of contracts and saved reviews write a metadata-only `retrieval` audit row (issues-log WR-11). Hosted tracing (Langfuse) of the vendored tool is a no-op ([corpai/legal/clausecheck/tracing.py](../corpai/legal/clausecheck/tracing.py)). |
| Gaps | `legal.save_review()` leaves `subject_ids` empty, so a review cannot be found by data subject **[recommendation]**. |

**What it does.** A finance owner job computes metric snapshots in SQL. The CFO signs and publishes them. The `report` graph reads signed snapshots and issue signals with the requester's own rights, the model writes prose around `{metric:…}` placeholders, code fills in and checks every number, and the report can be exported with a watermark ([corpai/agents/report/](../corpai/agents/report/), [corpai/metrics/](../corpai/metrics/); architecture §16 M3).

| | |
|---|---|

## 4. Sales prospect research and follow-up e-mail (`sales_profile`, `sales_web`)

**What it does.** A salesperson enters a company name. An isolated sub-agent searches and fetches public pages about that company (allowlisted domains only) and extracts a fixed-field company profile. Code scores fit (from the profile) and intent (from CRM interactions, as the user) and picks a playbook tier, and the local model writes a short strategy. A separate `/followup` request drafts an e-mail to a CRM contact and files it as a tier-3 `crm.send_email` proposal, which another person must approve ([corpai/agents/sales/graph.py](../corpai/agents/sales/graph.py), [corpai/agents/sales/web.py](../corpai/agents/sales/web.py)).

| | |
|---|---|
| Purpose | B2B prospecting and account follow-up for FleetPilot. |
| Legal basis | Art. 6(1)(f), assessed in [lia-sales-profiling.md](lia-sales-profiling.md). Decision D5: the platform profiles **companies**, not people. |
| Data subjects | Business contacts at prospects and customers (CRM); people named on public company pages (incidental); the salesperson and the approver. |
| Personal data | Company profile: none (enum and number fields only, [corpai/sales/profile.py](../corpai/sales/profile.py)). CRM: contact name, title, e-mail, phone, interaction history (L3). E-mail draft: contact name and title, subject and body. |
| Sources | Public pages (mock corpus `corpus_dir/web/pages.jsonl`, `*.example` hosts); `crm.*` as the user. |
| Recipients | The salesperson; the head of sales or the CEO as approver; the contact (simulated outbox `ops.outbox`). |
| Transfers | Profile extraction: `external` only when every prompt field is byte-identical to published pages and the session is L1 (`public_only`); otherwise `local`. Strategy and e-mail draft: `local`. |
| Retention | Web page text is never checkpointed (the sub-graph runs with `checkpointer=False`). Profile, scores and contacts stay in checkpoints until pruned. Proposals and outbox rows: no deletion. |
| TOMs | See the safeguards table in the LIA §5. |
| Gaps | There is no Art. 14 notice in e-mails, no opt-out line and no do-not-contact flag **[recommendation]**. |

The model writes a two-sentence note over the L2 part; a note containing any digit is replaced by fixed text ([corpai/hr/headcount.py](../corpai/hr/headcount.py), [corpai/agents/hr/headcount.py](../corpai/agents/hr/headcount.py)).

## 6. AI-assisted CV screening (`hr_screening`)

**What it does.** For one candidate, code removes identity and protected attributes from the résumé, asks the local model once per hard requirement of the requisition for *met / not met / unknown* with a verbatim quote, checks every quote, stores the evidence (L4), and waits for an HR person to decide (advance / hold / reject) with a written reason. There is no score, ranking or recommendation. The full description is in the [DPIA](dpia-hr-screening.md) §2.

| | |
|---|---|
| Purpose | Help recruiters check applications against a requisition's hard requirements consistently, with the evidence quoted. |
| Legal basis | Art. 6(1)(b): steps at the candidate's request before entering a contract (handling the application). Art. 6(1)(f) for the AI-assisted evidence extraction, balanced in the DPIA. Art. 22 does not apply because a person makes and records every decision, but the safeguards are kept as if it did (DPIA R3). Art. 9: the processing is designed not to use special-category data. Storing a résumé that contains it is covered only as far as Art. 9(2)(b) with the Swedish Data Protection Act ch. 3 s. 2 reaches **[counsel]**. Art. 10: no criminal-record data is processed. |
| Data subjects | Job candidates; HR staff on the requisition and the head of HR. |
| Personal data | Résumé text (`hr.candidates`, L3, trust untrusted); name, e-mail and phone (removed before the model); evidence per requirement with quotes (`hr.screening_evidence`, L4); decision, reason, decider and time (`hr.screenings`, L4). |
| Recipients | HR staff holding `req:<id>` and the head of HR (`hr._may_screen`, migration 090). Hiring managers do not see the evidence. |
| Transfers | `local` only. The database refuses evidence whose `model_route` is not `local` (CHECK in migration 090), but today `local` is DeepSeek. |
| Retention | None implemented for evidence and decisions. Recommended: the end of the recruitment plus 2 years **[recommendation, counsel]**. |
| TOMs | DPIA §5. |
| Gaps | DPIA R11 residual (redaction is pattern-based), candidate notice, retention. R10 (audit flags) was closed in the final review. |

| Recipients | The user (own spans, RLS); the platform admin (metadata only, `trace.read_meta`); heads (span counts for their own department, rows of fewer than 5 spans or fewer than 5 people suppressed, migration 102). |
| Transfers | None (no hosted tracer). |
| Retention | Indefinite; no deletion job **[recommendation: 30 days for text, 12 months for metadata]**. |
| TOMs | **[implemented]** Masking at span end; CHECK `spans_l4_metadata_only`; credential-like attr keys refused; `trace.write_span()` is the only write path.
